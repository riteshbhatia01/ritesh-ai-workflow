    Values & philosophy

    Values only count when they ship.

    Each one, paired with where it showed up in the work.

    01

    Craftsmanship & technical excellence

    Good architecture multiplies humans and AI alike. The stricter the patterns, the better the agent's output.

    Proof: Compose and Circuit adoption, so every Slack screen follows the same shape.

    02

    Pragmatism over perfection

    Ship early, measure, iterate. A tool's real value is the conversation it starts.

    Proof: post-migration surveys instead of assuming the migration worked.

    03

    Knowledge empowerment over control

    If only I know how something works, I've built a bottleneck. Write it down, teach it, then let go.

    Proof: 2 interns to FTE, and 2 mid-level engineers to senior.

    04

    Ownership without territory

    Own outcomes, not code. Anyone can touch "my" module.

    Proof: leading 8+ Staff and Senior engineers on work none of us owned alone.

    05

    Clarity & transparency

    Weekly updates, public threads, searchable decisions. ADRs beat hallway agreements.

    Proof: specs and ADRs for the Salesforce access-control model.

    06

    Customer focus

    An architecture is good when somebody's cheque deposit works the first time.

    Proof: a 35% lift in capture success for millions of users.

    i.

    Autonomy is earned, gate by gate

    Give the agent the full loop. Remove a human gate only after it has been boring for weeks.

    ii.

    Verify, don't trust

    "It compiles" isn't done. Done means built, installed, launched, screenshotted and tested.

    iii.

    The codebase is the prompt

    Every inconsistent file teaches the agent something you didn't mean to teach.

    iv.

    Fakes over mocks

    AI-written tests follow the team's real conventions. For us, that's hand-written fakes.

    v.

    AI augments, never replaces

    The agent handles the mechanical work. Intent, trade-offs and team context stay with people.

    01
    Code review5 min

    The PR review bottleneck moved, and it moved onto us

    AI made writing code cheap. It didn't make reading code cheap.

    +

    A year ago my biggest constraint was how fast I could write a feature. Now an agent can produce a working Compose screen, a presenter and tests before I finish a coffee. The constraint has moved downstream, to the person who has to review all of it.

    This is the conversation all over the Claude and Codex communities. Agents are good enough to open real PRs, and review capacity hasn't changed. The two bad outcomes are a growing queue of unreviewed PRs, or reviewers who give up and approve. Neither is acceptable for an app that millions of people open every day.

    What I'm doing about it

    • The agent reviews itself first. /code-review runs before a PR exists. A coroutine in the wrong scope, missing null handling, or a mock where we use fakes gets fixed before a human sees it.
    • Small diffs, always. Agents happily produce 1,500-line PRs, so I tell them to stop at layer boundaries and stack the PRs. A reviewer can hold 200 lines in their head.
    • Humans review intent, not syntax. Does this match the ticket? Is it the right abstraction? What breaks when the flag flips?
    • The PR description is an artifact. It says what changed, why, what was verified and what wasn't. "Not verified" is the line I read first.
    When code is cheap to write, review is the last place judgment happens before users see it. Protect that time.

    It's not solved. Review fatigue is real, and I don't think the answer is fully automated review. For now, the answer is making every human minute count.

    02
    Android4 min

    Agents can't see your Compose screen, so give them eyes

    Web developers get a browser in the loop. Android developers get an emulator, if they wire it in.

    +

    The most common complaint I hear from mobile developers: agentic coding works for backend and web, but struggles with Android. The reason is simple. Web agents can open a browser, look at the page and read the console. An Android agent usually gets nothing back except BUILD SUCCESSFUL.

    A screen can compile perfectly and still have a clipped button, a missing loading state, or a dark-mode color that disappears into the background.

    Closing the loop

    • Build, install, launch, look. My verification skill makes the agent install the APK, open the screen, screenshot it and check logcat before it can call a task done.
    • Snapshot tests as the contract. Visual diffs the agent can reason about, and before-and-after images for reviewers.
    • Previews for every state. Loading, Empty, Error, Content. Agents write them well once you require them.
    • Google's Android CLI. Android CLI 1.0, announced at I/O 2026, gives agents like Claude Code and Codex programmatic access to the Android Studio toolchain.
    An agent can only be as autonomous as its feedback loop is honest.

    Source: The Next Web, Android CLI 1.0

    03
    Android3 min

    Gradle is your agent's speed limit

    The model thinks in seconds and the build thinks in minutes. Design the loop around that.

    +

    Agents iterate: edit, check, fix, check again. On a large modular codebase every check can mean a multi-minute Gradle run. An agent that makes 15 attempts spends most of the session waiting, and it often loses track of what it was doing.

    What helped

    • Scope every task to a module. :feature-x:compileDebugKotlin, not assembleDebug. CLAUDE.md spells out the exact commands for each module.
    • Cheap checks first. Compile, then unit tests for the module, then the full build once at the end.
    • Don't invent versions. Agents love to "fix" a build by bumping a library. A skill forces them to read the version catalog and the real error first.
    • Parallel isn't free. Two worktrees means two Gradle daemons and twice the memory on a laptop.

    The mobile build system was designed for humans who build a few times an hour. Agents build a few times a minute. Every Android team will feel that gap this year.

    04
    Claude Code4 min

    Context drift: why your agent forgets the rules two modules over

    One giant CLAUDE.md doesn't scale. Layer context the way you layer your architecture.

    +

    Early on, the agent would write a perfect Circuit presenter in one module. Then it would write a classic ViewModel with LiveData in the next, because a nearby legacy file "looked like the pattern". The model wasn't wrong. It copied what it saw. The problem was what I'd let it see.

    Layering context

    • Root CLAUDE.md for universal rules: architecture, fakes over mocks, and build commands. Keep it short.
    • Module-level notes where the rules differ. Legacy modules say so: "Don't copy patterns from here."
    • Skills for patterns, not facts. "How we build a screen" loads when it's needed.
    • Memory for corrections, so they don't come back next week.
    The codebase is the prompt.

    Context engineering is one of the biggest topics in the Claude Code community right now, and I think it's because this is where a lot of the remaining quality gap is.

    05
    Community4 min

    Claude vs Codex on mobile: the wrong question, mostly

    Acceptance rates differ by agent. What they don't measure is what you'll maintain next year.

    +

    For mobile there's finally some data. A February 2026 study of 2,901 AI-authored pull requests across 193 Android and iOS open-source repos found big differences on Android. Codex PRs were accepted 76.8% of the time, compared with 42.3% for Cursor and 28.0% for Copilot. iOS acceptance was more uniform across agents.

    That's interesting, but I'd be careful about turning it into a buying decision.

    What acceptance rate does and doesn't tell you

    • It measures mergeability, not maintainability. A merged PR can still add a pattern your team spends a year removing.
    • It depends on the task mix. Small, well-scoped fixes get merged more. The agent that tries harder issues can look worse.
    • It ignores your conventions. On a Circuit plus fakes codebase, the agent that follows your skills beats the one with the better benchmark.

    How I choose

    Claude Code is my daily driver because of the harness around the model: skills, hooks, plan mode, worktrees and MCP. The more useful question isn't "which agent is best?" It's "which agent produces the diff that's cheapest for my team to review?" That ties straight back to the review bottleneck. Claude and Codex are both available as coding agents on GitHub now, so you don't have to pick just one.
